## 交換 v2（検証済みの参照処理）

v1 は端末内の仮受け取りを支える既存画面として維持する。v1の署名に含まれない所有権バージョンを後付けして認証済みとは扱わない。v2 は別の厳格な名前空間を使用する。実画面の保存済みv1記録は書き換えない。

|位置|長さ|署名する値|
|---|---:|---|
|0|8|TONARI、0、バージョン2|
|8–183|176|show、双方の公開鍵、双方のタイル実体ID、16バイトnonce（v1と同位置）|
|184|4|issuedAt|
|188|4|expiresAt（受諾できる時刻、発行後最大120秒）|
|192|32|policy（チェーン・プログラム・show・制限を固定するポリシーのハッシュ）|
|224|4|versionA|
|228|4|versionB|
|232|4|settleBy（確定を許可する期限、発行後最大7日）|
|236|4|予約領域、常に0|

整数はu32 little endian。Aは全240バイトに署名。Bは `TONARI/v2/swap-accept\0` + SHA256(body) + Aの署名に署名する。双方署名付き368バイト。QRは `TONARI2:K/O/R:` の厳密なbase64url（53/416/501文字）。v1受信機はv2を拒否し、v2受信機もv1を拒否する。QR描画・画像復号のライブラリは両形式を区別して読めるが、型と署名の検証は利用側で必須。

通信復帰後にexpiresAtを過ぎていても、双方が署名したsettleByとshowの期限まで参照処理が検証する。受諾時刻を証明できるとは主張しない。参加者は「この内容ならsettleByまで確定してよい」と署名する。端末のunsigned acceptedAtは検証に使わない。署名期限の延長は新たな署名が必要。将来の画面にはこの違いを明示し、showが選ぶ短い上限を適用する。

`SettlementModel` は、署名、show/policy、期限、正しい現在の所有者、署名されたバージョン、ペア上限、nonce、端末別上限、確定時刻基準120秒制限を検証する。同一の記録の再送は一回だけ反映。同時に届く競合は先に通った方を反映し、後続を拒否する。失敗時は一切の状態を変更しない。片方だけ交換された状態を作らない。結果は `MODEL_SETTLED / ownershipFinal:false`。Solana上の確定ではない。

参照モデルの初期所有権・時間・policyは呼出元の信頼済みテスト入力。公開APIではない。永続化、アカウント所有者/PDA制約、show policyの正規ハッシュ導出、instructions sysvar、CPI拒否、実際のEd25519検証命令、ローカルvalidator、devnet接続は次段階。正当な相手への補償・不正者凍結は、無制限な交換や補償を許す抜け道にせず、別の会場承認と上限が必要。

Rust `ownership.rs` は同じ240バイトの読み取りと、状態を変更せず交換計画を返す核。JavaScriptが出力した公開テスト用hex fixtureを使用する。7テストを作成したが、Work環境にrustcが無いため未コンパイル。既存 `signature_binding.rs` の5テストも同様。核の検査は署名検証・PDA検証を代替しない。Anchorプログラムと呼ばない。

## もも＆るる（新しいブランド画面）

ピンクのもも、ラベンダーのるる。ハートのピースを分けあうオリジナルSVG。外部画像・フォントを読み込まず、PWAに保存する。参照JPEGはコネクタのUTF-8限定により閲覧できなかったため、指示の形・色・構図を基に新規のSVGを制作した。画像を閲覧済みとは扱わない。

index / phone / exchange / operations にパステル背景、丸いカード、片手で押せる48px以上のボタン、あたたかい案内を追加。indexとexchangeに3ステップ案内。既存の交換成功・復元処理がひよこをswap状態にする。rare/completeは案内部品として実装済みで、未実装のレア配布・ゲーム完了からは発火しない。スクリーンショットも「部品のプレビュー」と本物の交換を区別する。動きを抑える設定に対応する。

主要色組合せの静的コントラストは5.93〜10.85（通常文字AA4.5以上）。これは全ページのアクセシビリティ監査の合格を意味しない。新画面の実ブラウザ・オフライン確認とbefore/afterスクリーンショットはBot残作業。

## 次段階のトランザクションサイズ制約

v2本体240＋署名128を、Ed25519命令352/230バイトに加えてsettle_swap引数にも重複して入れると、アカウント数によってSolanaのトランザクションサイズ上限を越え得る。次のAnchor実装では、直前の自己完結した2つの検証命令から本体と署名を取り出し、厳密なprogram/accounts/offset/length検査・body hashとBの受諾ドメイン検査を行う。settlement引数に368バイトpacketをもう一度載せない。show/所有権/ticket/pair/nonceのPDAを本体から束縛し、CPIを拒否する。署名命令が実行された実トランザクションと、完全なserialized byte長をvalidatorで検査するまではサイズ適合・チェーン確定を主張しない。
